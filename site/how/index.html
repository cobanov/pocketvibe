How PocketVibe works

Everything you see in PocketVibe is a web page: the menus, and every game. The handheld runs a small browser and a small web server side by side, with no internet needed once a game is downloaded. Here is how the pieces fit.

A browser made for a handheld

three.js draws 3D with WebGL, and WebGL lives in browsers. So a handheld needs a browser, but Chrome or Firefox are too heavy for one and expect a desktop around them. PocketVibe uses WPE WebKit: the engine behind Safari, in the version made for set-top boxes, car dashboards and other small devices. It has no window and no address bar, and draws straight to the screen. Cog is the smallest browser built on it: one page, full screen.

A frame of a game goes down these layers to reach the screen:

  1. The gamethree.js, in JavaScriptWebGL
  2. WPE WebKitinside Cog, full screenOpenGL ES
  3. Mesa Panfrostthe open-source driver for the GPU
  4. Mali-G31 GPUand the screen, through ROCKNIX's Sway

Getting the engine onto the handheld

ROCKNIX is a lean system for handhelds: it has no WPE, and no package manager to install one with. So PocketVibe brings its own: a small Debian file system with WPE WebKit, Cog and the Mesa graphics drivers, packed into a 147 MB download. That is what the first start downloads and unpacks (690 MB on the SD card).

PocketVibe runs the browser inside that Debian with Linux's own tools for containers: a private set of mounts and pivot_root, so the browser sees Debian as its whole system. A plain chroot would be simpler, but WebKit puts every page in a sandbox (bubblewrap), and bubblewrap refuses to work inside a chroot. This way, games run sandboxed.

What runs on the handheld

PocketVibe.sh

What the Ports menu starts. It sets PocketVibe up the first time, starts the service, opens the browser, and opens it again if it ever crashes.

pocketvibed

A small web server in Python on 127.0.0.1:8730: the launcher's files, and an /api to the library, the store, downloads, settings and updates.

Cog

The browser. It opens the launcher, which is a web page like any other, and the games from there.

Each game is a folder of web files built with Vite, and the service gives each one its own address on the handheld: 127.0.0.1:20066, 127.0.0.1:21544, and so on. Browsers keep saved data per address, so every game gets its own saves, and no game can read another's.

What happens when you press A

  1. The launcher asks the service to start the game: POST /api/launch/brick-breaker.
  2. The service starts a small server for that game on its own address, and answers with where the game is.
  3. The browser goes there, to the game's shell: 127.0.0.1:20066/__pocketvibe__/play.html.
  4. The shell shows the game's cover and name, and loads the game in a frame sized for the screen.
  5. The game's device layer sets up WebGL, reads the buttons and starts the game loop. Once the first frames are drawn, the cover fades away.

Holding Start and Select takes you back. Those two buttons are read by the service straight from Linux, not by the browser, so they work even if a game freezes. The service tells Cog to open the launcher; held for three seconds, it quits PocketVibe.

The buttons reach games through the browser's Gamepad API. One trick: WebKit lets a page play sound only after a real key press, and gamepad buttons do not count. So the service keeps a tiny virtual keyboard and taps F13, a key nothing uses, which unlocks the sound.

On Android

The launcher, the shell and the games are the same files. Only the layers under them change:

ROCKNIXAndroid
Browser engineWPE WebKit, in CogAndroid System WebView (Chrome's engine)
Local servicepocketvibed, in PythonThe same API, in Kotlin, inside the app
ButtonsGamepad API, through libmanetteAndroid's key events, turned into the keys pages read
Graphics driverMesa PanfrostThe handheld maker's own

That last row is why the same game can run smoother on an Android handheld: Chrome's graphics path is very mature, and the maker's driver is tuned for its chip.

The store, and this website

The store runs on Cloudflare: a small Worker, a D1 database of games and versions, and R2 for the game zips and covers. The handheld reads the store's catalog.json. npx pocketvibe publish builds a game, packs it with its listing and cover and uploads it; once it is reviewed, it joins the catalog.

The handheld on the home page runs the very same launcher. In your browser, a service worker answers in place of pocketvibed, which is why the demo behaves exactly like the real thing.

The hard part: speed

The setup above is simple. Getting 60 fps out of a small GPU through a browser engine is not. Typical three.js code ran at 3 to 6 fps on the handheld. So we measured what every cost does there, one at a time: triangles, draw calls, lights, shadows, the CPU time large indexed meshes take in WebKit, and more. Those numbers became the rules the AI tools follow when they write a game, and games that follow them run at 60.

The measured limits are on Make a game, and the code is on GitHub.
